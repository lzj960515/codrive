# 任务文档

新普通任务在登记前先写入项目仓库内的 Markdown 文件，登记 `taskDocumentPath`，值为相对仓库根目录的路径。文档是该任务的正文；执行、审查和规划每轮都从主项目目录按路径读取当前文件。修改任务内容时直接编辑原文件，后续回合读取修改后的内容。

## 写法

标题说清要完成的业务动作和对象。正文以最少的文字回答“交付什么”和“如何确认完成”；只有会影响判断时才写范围、前置结果、已有决定或资料位置。验收条件检查可观察结果与关键不变量，保留当前目标所需的产品行为、数据边界、发布条件和已确认的安全约束；常规工程规范沿用项目约定。使用自然中文，一项事实写一次；代码标识符、路径和没有自然中文称呼的固定名称保留原文。

```markdown
# <任务名称>

## 交付结果

<完成后谁能做什么，或系统会出现什么可核实的变化。写清必要边界。>

## 验收条件

- <在具体场景下能观察到的结果或必须保持的不变量。>
- <另一项独立、必要的结果。>
```

确有前置交付时，加“前置结果”，指出依赖任务及其必须先交付的结果。需要来源时，加“依据”，给出可查找的路径、链接或已确认决定。已有规格只引用与本任务有关的部分；任务文档仍须独立说清本任务的结果与验收。测试和文档只有构成交付证据或用户结果时才写入验收条件，并说明它们证明什么。

登记前读回文件，确认路径指向项目仓库内实际存在的非空 Markdown 文件，内容足以让执行者独立判断完成与否。登记对象只传标题、`taskDocumentPath` 和必要的里程碑归属；任务的结果与验收保留在文档中。

## 旧任务

没有 `taskDocumentPath` 的历史任务继续以任务 JSON 中的 `description` 和 `acceptanceCriteria` 为正文。编辑此类未开始任务时沿用原字段；新建任务使用文档路径。
